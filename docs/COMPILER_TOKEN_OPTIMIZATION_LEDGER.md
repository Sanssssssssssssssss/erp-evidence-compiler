# Evidence Compiler：保持已测正确性的 token 优化笔记

更新：2026-09-07。当前实现版本：`15f3d1d`。本笔记集中记录方法、前后用量、准确性验收和收益边界；失败、成本增加和用量未知同样保留。

**目前最可靠的结论：同一候选的首次 Verifier 去重，三组对照合计减少 12.91% token。Executor 批量绑定在制造单例中观察到 21.20% 的阶段用量下降。尚无当前完整 Compiler 在相同条件下统一节省多少百分比的结论。**

这里的“性能相同”指本批案例的逐 CHECK 结论、审核范围和 reasoning 配置一致，不是统计意义上已证明普遍准确率等效，也不代表延迟、费用相同。下述百分比分属不同阶段，不能相加或相乘。

## 统一记录口径

- 模型：`deepseek/deepseek-v4-flash`；相关对照保持 `high`。省 token 的方法是减少重复表示和交互，不是降低 reasoning 或删掉审核材料。
- `total_tokens = prompt_tokens + completion_tokens`。输入包含缓存；reasoning 已包含在输出中，不能再加一次。
- 节省率 = `(旧版 total − 新版 total) / 旧版 total × 100%`。合计使用总量计算，不平均各案例百分比。
- 优先同一来源、密封计划、候选、模型配置的配对对照；历史对照和单案例信号明确标注。
- 分开记录 Task Compiler、Executor、首次 Verifier、返工及复核。重放阶段的新增 0 token 不意味着产品把该阶段优化到免费。
- 缺失 usage、流中断和异常零值按未知或已知下限记录；不将未完成运行算成同等质量的成功样本。
- 正确性验收与 token 口径一起保留。成功案例之外的失败不能从整轮实验开销中删除；已知 token 节省也不等于美元费用节省。

## 优化 1：共享 Verifier 的重复上下文

版本：`b78a7f5 → 6f2c51a`。生产内容净增 25 行，无新 Agent、依赖或工具。

方法：完全相同的合同字段只提供一次，各 CHECK 保留差异；同一个 Claim、Binding、Witness 正文按既有 ID 只提供一次，各 CHECK 的引用和终端闭包保持完整。原文、全局计划、政策及边界保留，候选仍在原文独立初审后揭示。

对照：每例每版各一次真实运行；首次 Verifier 输入使用相同原文、计划和 Executor 候选，每版均为 2 个 provider 回合。两版最终各 **27/27 CHECK** 正确。制造例两版首次都要求修复目标 MO 的缺失证明，随后同一 CHECK 返工通过；因此 27/27 指最终结果，不是首次就全部通过。

| 首次 Verifier | 旧版 token | 去重版 token | 少用 token | 减少 |
| --- | ---: | ---: | ---: | ---: |
| 发票 | 111,869 | 97,532 | 14,337 | 12.82% |
| 采购 | 116,041 | 100,653 | 15,388 | 13.26% |
| 制造 | 84,155 | 73,583 | 10,572 | 12.56% |
| 合计 | **312,065** | **271,768** | **40,297** | **12.91%** |

输入 token 合计 `242,208 → 205,357`，减少 **15.21%**。这组是本笔记的主要收益依据，但每例每版只有一次，尚无重复采样的置信区间。

若包含制造的 Executor 返工和后续复核，账面是 `462,050 → 378,003`，减少 **18.19%**。两次返工诊断和执行轨迹不同，不能将额外差额全部归因于上下文去重，故不使用 18.19% 作为主要效果。

两版缓存热度不同：上述包含返工的未缓存输入反而从 `96,006` 增到 `148,720`。因此本轮不能声称美元费用同步下降。

## 优化 2：Executor 批量绑定字段、精简工具回执

版本：`6f2c51a → e77ebfb`。生产内容净增 45 行。

方法：用 `bind_record_fields` 一次选择同一记录的多个字段；模型继续选择证据和解释含义。Runtime 逐字段复用原校验，读取真实值、生成引用，回执省去重复来源和 locator；完整 Claim 留在证明存储中。没有按案例或业务答案写分支。

| 案例 / Executor 阶段 | 历史 token | 新 token | 观察变化 | 能否记作保持已测正确性的节省 |
| --- | ---: | ---: | --- | --- |
| 制造 | 327,515 | 258,095 | 少 69,420；**减少 21.20%**；8→7 个回合 | **单例历史对照信号。** 前后逐 CHECK 与 Kernel 均 7/7 正确，首轮 Executor payload 相同；Verifier 历史版本不同，不能推广成稳定整体收益。 |
| 发票 | 1,032,850 | 608,695 | Executor 阶段减少 **41.07%**；18→11 个回合 | 暂不纳入主要收益：当轮最终 Verifier 缺字段，整体 `NON_CONVERGED`。后来固定候选续跑修复了 11 项，但没有重做完整成功运行的配对成本对照。 |

另有零 API 的历史字段操作重放，验证批量调用的完整 Claims、值、类型、元数据、ID、错误与旧工具一致。这证明字段工具的等价性；JSON 字符数或工具调用次数下降不直接等于 token 节省。

## 修复 3：Verifier 用工具提交，允许一次协议纠正

版本：`e77ebfb → 15f3d1d`。生产内容净增 42 行。此项先记为可靠性修复，不记为已证明的 token 优化。

方法：用 `submit_verification` 复用原输出 schema。第一次缺字段将具体错误反馈给模型，允许其自行纠正一次；再次失败就停止。成功后直接返回已验证对象，不要求模型再抄一遍最终 JSON。代码不代填 `status`，原文优先复核与 Kernel 保留。

验证：原发票失败草稿在受控续跑中一次纠正成功，11/11；采购和制造在固定候选上重新复核，9/9、7/7。离线 250 passed。这是一次原失败继续实验和两次新 Verifier 复核，不是三次全新完整 child run。

| 观察 | 旧 token | 新 token | 解释 |
| --- | ---: | ---: | --- |
| 采购 Verifier，同一固定候选，前后 9/9 | 77,498 | 84,523 | **增加 7,025，增加 9.06%**。保留成本上升；单次随机运行不足以证明固定开销。 |
| 发票缺字段纠正 | 不可比 | 65,821 | 继续原草稿，只付本次纠正调用；不能与首次完整审核比较节省率。 |
| 制造 Verifier | 126,094 | ≥71,888 | 新运行有一次流中断没有 usage，完整总量未知，不给精确节省百分比。 |

本轮另外三次 `tool_choice=required` 的尝试被 thinking 路由拒绝，最终已移除该参数。失败 usage 未返回，完整保留于账目。不能用缺失用量制造成本下降。
