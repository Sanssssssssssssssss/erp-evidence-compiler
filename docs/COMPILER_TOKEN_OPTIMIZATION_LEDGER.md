# Compiler 优化简记

更新：2026-09-07。

**一次运行参考：制造约 40 万 token。** 执行＋复核实测 38.4 万，规划历史约 2 万；40 万是预算估算，不是所有案例的平均值。

| 最近的执行＋复核 | 用量 | 结果 |
| --- | ---: | --- |
| 制造 | 38.4 万 | 成功，7/7 正确 |
| 采购 | 至少 29.2 万 | 成功，9/9 正确；部分用量缺失 |
| 发票（最新降耗实验） | 34.1 万 | 提交成功；自建额外约束下仍有证据误判 |

以上不含规划，包含缓存输入。最新发票：Executor **23.76 万**、Verifier **10.36 万**，缓存输入共 17.86 万。

范围更正：ERP-Bench 未要求写入或匹配 fiscal_position_id，这是自建材料和旧模板加的约束。以后不把它当 benchmark 必查项；税额检查保留。旧材料确实写了该约束，因此旧运行“把缺失当空值”的误判记录保留，不能倒改成全对。详见[规则核对](COMPILER_BENCHMARK_SCOPE_20260907.md)。

本轮把计划中的多步算术合成一次工具调用，Executor 用 low：请求 **11→5 次**，Executor **50.34→23.76 万（-52.8%）**，执行＋复核 **60.15→34.12 万（-43.3%）**。只测发票一例；缺字段提醒未奏效。降幅是含缓存 token，未缓存输入增加，不能等同账单下降。

**我们改了什么：**

- Verifier 去掉重复合同和证明：首次复核省 **12.9%**；三组对照最终均 27/27 正确。
- Executor 一次绑定多个字段：制造执行阶段省 **21.2%**；单例历史对照，前后均 7/7 正确。
- Verifier 缺字段时允许自己改一次：修复提交失败；尚未证明省 token，采购单例反而增加 **9.1%**。

这些是不同阶段的结果，不能相加成整体节省率。

2026-09-07 新税票工具实验：官方脱敏示例跑一个真实模型 child，规划 **1.445万**、Executor low **2.845万**、Verifier high **2.131万**，共 **6.421万 token**；2/2 正确保持证据不足，Kernel 重放一致。此例更小且没有真实阿里云查询，不与旧 ERP 发票案例计算节省率。详见[税票实验](TAX_INVOICE_EXPERIMENT.md)。
